## 1. 项目概述

本项目是一个通用的**后台管理系统脚手架**，核心解决「谁（用户）能做什么（权限）」的问题。采用前后端完全分离架构，前端独立构建部署，后端提供无状态 RESTful API，通过 JWT 承载用户身份。

### 1.1 核心目标

- **通用权限底座**：用户、角色、菜单、部门、字典等基础能力开箱即用。
- **细粒度权限控制**：支持到「菜单级 / 按钮级 / 接口级 / 数据级」四个层次。
- **前后端双重校验**：前端控制菜单/按钮显隐（体验），后端校验接口权限（安全）。
- **可扩展**：分层清晰，业务模块可基于此脚手架快速叠加。

### 1.2 权限控制的四个层次

| 层次 | 控制对象 | 实现方 | 说明 |
| --- | --- | --- | --- |
| 菜单级 | 页面/路由是否可见 | 前端 | 登录后拉取用户菜单树，动态生成路由 |
| 按钮级 | 页面内操作按钮显隐 | 前端 | 通过 `v-permission` 指令 + perms 标识 |
| 接口级 | API 是否可调用 | 后端 | Casbin / 中间件校验，**安全兜底** |
| 数据级 | 能看哪些行数据 | 后端 | 按 data_scope（全部/本部门/本人）过滤 |

> **关键原则**：前端的权限控制只是「体验优化」，绝不能作为安全边界。任何权限校验都**必须在后端接口层再做一次**，否则可绕过前端直接调接口。

## 3. 系统架构设计

采用经典分层架构，请求自上而下流转：

```
浏览器（Vue SPA）
      │  HTTPS / JSON + Bearer Token
      ▼
Nginx（静态托管 / 反向代理 / 负载均衡 / CORS / 限流）
      │
      ▼
Gin 应用层
  ├─ Middleware：Recovery / Logger / CORS / JWT鉴权 / Casbin权限 / 限流
  ├─ Router      路由注册与分组
  ├─ Controller  参数绑定校验、调用 Service、组装响应
  ├─ Service     业务逻辑、事务编排
  ├─ Repository  基于 GORM 的数据访问
  └─ DTO/VO      请求/响应数据结构
      │
      ├──────────────┐
      ▼              ▼
   MySQL          Redis
  （持久化）     （缓存/会话）
```

> 详见对话中的「系统分层架构图」。

### 3.1 分层职责

- **Controller**：只做 HTTP 相关的事——绑定参数、调用 Service、返回统一响应，不写业务逻辑。
- **Service**：核心业务逻辑与事务边界，是权限判断、数据组装的主战场。
- **Repository**：纯数据访问，屏蔽 GORM 细节，便于测试与替换。
- **Model**：GORM 实体，对应数据库表。
- **DTO/VO**：入参（DTO）与出参（VO）与数据库实体解耦，避免敏感字段（如 password）泄露。

## 4. RBAC 权限模型

### 4.1 模型核心

用户**不直接持有权限**，而是通过「角色」这个中间层间接获得权限。这样做的好处：调整权限只需修改角色配置，无需逐个改用户。

```
用户 User  ──(M:N)──  角色 Role  ──(M:N)──  菜单/权限 Menu
    │                    │
   归属                数据范围
    ▼                    ▼
 部门 Dept  ◄──(M:N)──  角色 Role
```

- **用户 ↔ 角色**：多对多（一个用户可有多个角色，如「管理员+审核员」）。
- **角色 ↔ 菜单/权限**：多对多（角色勾选一批菜单和按钮权限）。
- **用户 → 部门**：一对多（用户归属一个部门，部门为树形结构）。
- **角色 → 数据范围**：通过 `data_scope` + `role_dept` 关联表实现数据级权限。

> 详见对话中的「RBAC 权限模型关系图」。

### 4.2 数据权限范围（data_scope）

角色的 `data_scope` 字段定义该角色能看到哪些数据：

| 值 | 范围 | 说明 |
| --- | --- | --- |
| 1 | 全部数据 | 不做过滤 |
| 2 | 自定义数据 | 按 `role_dept` 关联的部门集合过滤 |
| 3 | 本部门数据 | 只看用户所在部门 |
| 4 | 本部门及子部门 | 部门树向下递归 |
| 5 | 仅本人数据 | 只看 `create_by = 当前用户` |

### 4.3 超级管理员

约定 `code = "admin"` 的角色为超级管理员，在后端鉴权中间件中直接放行，**跳过所有权限校验**，避免自己把自己锁死。

## 5. 鉴权与授权流程

### 5.1 登录换取令牌（阶段一）

1. 用户提交账号 + 密码（+ 图形验证码）。
2. 后端用 bcrypt 比对密码哈希。
3. 校验通过 → 签发 JWT（Payload 含 userID、username、roles、过期时间）。
4. 前端将 Token 保存在本地缓存中，后续请求携带。

### 5.2 携带令牌访问接口（阶段二）

1. 请求在 `Authorization: Bearer <token>` 头中携带令牌。
2. **JWT 中间件**：验签 + 校验是否过期 + 查 Redis 黑名单 → 无效则返回 `401`。
3. **Casbin 权限中间件**：根据 `用户角色 + 请求路径 + 方法` 匹配策略 → 无权限返回 `403`。
4. 校验全部通过 → 进入 Controller 执行业务，返回数据。

> 详见对话中的「JWT 登录与鉴权流程图」。

### 5.3 关键安全点

- **密码**：只存 bcrypt 哈希，绝不明文；数据库泄露也无法反推。
- **Token 过期**：Access Token 短时效（如 2h）+ Refresh Token 长时效（如 7d）续期。
- **登出/踢人**：将未过期 Token 写入 Redis 黑名单直至其自然过期。
- **前端路由守卫**：未登录跳登录页；已登录但无该菜单权限跳 403 页。

## 6. 数据库表结构设计

> 完整字段与关系详见对话中的「数据库 ER 表结构图」。以下为表清单与建表要点。

### 6.1 表清单

| 表名 | 中文名 | 说明 |
| --- | --- | --- |
| `sys_user` | 用户表 | 登录账号主体 |
| `sys_role` | 角色表 | 权限集合载体 |
| `sys_menu` | 菜单/权限表 | 目录/菜单/按钮三合一，树形 |
| `sys_dept` | 部门表 | 组织架构，树形 |
| `sys_user_role` | 用户-角色关联表 | 多对多 |
| `sys_role_menu` | 角色-菜单关联表 | 多对多 |
| `sys_role_dept` | 角色-部门关联表 | 数据权限范围 |
| `sys_dict_type` | 字典类型表 | 数据字典分类 |
| `sys_dict_data` | 字典数据表 | 字典键值项 |
| `sys_oper_log` | 操作日志表 | 记录增删改等操作 |
| `sys_login_log` | 登录日志表 | 记录登录行为 |

### 6.2 通用设计约定

- **主键**：`id BIGINT UNSIGNED AUTO_INCREMENT`。
- **软删除**：主表带 `deleted_at DATETIME NULL`，GORM `gorm.DeletedAt` 自动处理，不物理删除。
- **审计字段**：`created_at` / `updated_at` / `created_by` / `updated_by`。
- **状态字段**：`status TINYINT`，统一约定 `0=停用 / 1=正常`。
- **字符集**：`utf8mb4`，排序规则 `utf8mb4_general_ci`。
- **索引**：`username`、`role.code`、`dict_type.type` 建唯一索引；外键字段建普通索引。
- **敏感字段加密**：`sys_user` 的 `email` / `phone` / `nickname` 采用 AES-256-GCM 加密存储，并为 `email` / `phone` 增设 HMAC 盲索引列以支持精确查询与去重（详见 6.4）。

### 6.3 sys_menu 关键说明

`sys_menu` 通过 `type` 字段区分三种节点，一张表承载整个菜单权限树：

- `type=1` 目录（如「系统管理」）
- `type=2` 菜单（如「用户管理」，对应一个页面 `component`）
- `type=3` 按钮（如「用户新增」，只有 `perms` 权限标识如 `system:user:add`，无路由）

前端根据菜单树生成路由和侧边栏，根据 `perms` 集合控制按钮显隐。

### 6.4 敏感字段加密存储方案（AES-256）

出于数据安全与合规（如个人信息保护）要求，用户表中的**邮箱、手机号、昵称**等个人敏感信息不以明文落库，采用 **AES-256-GCM** 对称加密后存储密文。

#### 6.4.1 加密算法选型

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 算法 | AES-256-GCM | 认证加密（AEAD），同时保证机密性与完整性 |
| 密钥长度 | 256 位（32 字节）| 由配置/密钥管理系统注入，**绝不硬编码进代码** |
| Nonce/IV | 每次加密随机生成 12 字节 | 随密文一起存储，保证相同明文每次密文不同 |
| 存储格式 | Base64( nonce ‖ ciphertext ‖ authTag ) | 拼接后整体 Base64，存入 varchar 字段 |

> 为什么用 GCM 而不是 CBC：GCM 自带完整性校验（authTag），能发现密文被篡改；且相同明文因随机 Nonce 产生不同密文，避免泄露"两人手机号相同"这类信息。

#### 6.4.2 加密字段与列长度调整

加密后为 Base64 密文，长度显著大于明文，字段类型需放大：

| 字段 | 明文示例 | 存储列 | 建议长度 | 说明 |
| --- | --- | --- | --- | --- |
| `email` | user@x.com | `email` (varchar) | 255 | 存 AES 密文 |
| `phone` | 13800138000 | `phone` (varchar) | 128 | 存 AES 密文 |
| `nickname` | 张三 | `nickname` (varchar) | 255 | 存 AES 密文 |

#### 6.4.3 密文无法直接查询的问题与「盲索引」

**核心难点**：`email`、`phone` 加密后是随机密文，无法再用 `WHERE phone = '138...'` 精确查询，也无法建唯一索引做去重校验。

解决方案：为需要**精确查找/去重**的字段额外增加一列 **HMAC 盲索引（blind index）**：

- 新增列 `email_hash CHAR(64)`、`phone_hash CHAR(64)`，存储 `HMAC-SHA256(明文, 独立HMAC密钥)` 的十六进制值。
- HMAC 是确定性的：相同明文 → 相同 hash，因此可 `WHERE phone_hash = HMAC(输入)` 精确命中，也可在 hash 列建**唯一索引**保证手机号/邮箱不重复。
- HMAC 不可逆，即便 hash 列泄露也无法反推明文；且使用独立于 AES 的密钥，进一步隔离风险。
- `nickname` 一般只做展示、不做精确查询，可不建盲索引（若需模糊搜索，加密字段无法 LIKE，需另做方案，见 6.4.5）。

调整后的用户表相关列：

| 列 | 类型 | 索引 | 用途 |
| --- | --- | --- | --- |
| `email` | varchar(255) | — | AES 密文 |
| `email_hash` | char(64) | UNIQUE | 邮箱盲索引，查询/去重 |
| `phone` | varchar(128) | — | AES 密文 |
| `phone_hash` | char(64) | UNIQUE | 手机号盲索引，查询/去重 |
| `nickname` | varchar(255) | — | AES 密文 |

#### 6.4.4 加解密落地方式（GORM 自动化）

推荐在 GORM 层自动完成加解密，业务代码无感知，两种方式二选一：

- **方式 A（推荐）自定义字段类型**：为敏感字段定义实现 `Scanner`/`Valuer` 接口的加密类型（如 `EncryptedString`），`Value()` 时加密写库、`Scan()` 时解密读出。盲索引在 GORM `BeforeSave` 钩子里由明文计算并回填。
- **方式 B GORM 钩子**：在模型的 `BeforeCreate`/`BeforeUpdate` 钩子中加密并计算 hash，`AfterFind` 钩子中解密。

无论哪种，加解密工具统一放在 `pkg/crypto/`，密钥从配置注入。

#### 6.4.5 注意事项

1. **密钥管理是重中之重**：AES 密钥与 HMAC 密钥应从环境变量 / KMS / 密钥管理服务注入，严禁写死在代码或提交到 Git。生产建议接入云 KMS。
2. **密钥轮换**：更换密钥需对存量数据重新加密（读旧密钥解密 → 新密钥加密），设计时预留 `key_version` 字段可平滑轮换。
3. **模糊搜索受限**：加密字段无法 `LIKE '%关键字%'`。若后台需按手机号/邮箱模糊搜索，只能做前缀盲索引或改为精确查询；请与产品确认交互。
4. **日志脱敏**：Logrus 输出日志时，涉及手机号/邮箱务必脱敏（如 `138****8000`），切勿把明文或密文打进日志。
5. **返回前端脱敏**：VO 返回时按需脱敏展示，避免完整明文在前端网络请求中暴露。

### 8.1 前端权限落地方式

- **动态路由**：登录后调 `/user/menus` 拉取菜单树，`permission store` 将其转为路由并 `addRoute`。
- **按钮权限**：`v-permission="'system:user:add'"` 指令，比对用户 perms 集合决定是否渲染。
- **请求拦截**：Axios 请求拦截器自动注入 Token；响应拦截器统一处理 401（跳登录）/ 403（提示无权限）。

### 9.3 核心接口一览

| 模块 | 接口 | 说明 |
| --- | --- | --- |
| 认证 | `POST /auth/login` | 登录，返回 Token |
| 认证 | `POST /auth/logout` | 登出，Token 入黑名单 |
| 认证 | `GET /auth/captcha` | 获取图形验证码 |
| 认证 | `GET /auth/info` | 获取当前用户信息 + 权限 |
| 认证 | `GET /auth/menus` | 获取当前用户菜单树 |
| 认证 | `PUT /auth/password` | 修改自己的密码 |
| 认证 | `PUT /auth/profile` | 修改自己的资料（昵称/邮箱/手机号/性别） |
| 认证 | `POST /auth/avatar` | 上传头像（multipart，JPG/PNG/GIF/WEBP，≤2MB） |
| 用户 | `GET/POST/PUT/DELETE /users` | 用户增删改查 |
| 用户 | `PUT /users/:id/password` | 重置他人密码 |
| 用户 | `PUT /users/:id/roles` | 分配用户角色 |
| 用户 | `GET /users/export` | 导出用户 CSV（手机号/邮箱脱敏，上限 1 万条） |
| 角色 | `GET/POST/PUT/DELETE /roles` | 角色增删改查 |
| 角色 | `GET /roles/all` | 全部启用角色（下拉用，不分页） |
| 角色 | `GET /roles/:id` | 角色详情（含已分配菜单与部门 ID） |
| 角色 | `GET/PUT /roles/:id/menus` | 查询 / 分配角色菜单权限 |
| 角色 | `PUT /roles/:id/data-scope` | 设置数据权限范围 |
| 菜单 | `GET /menus/tree` | 菜单树（含隐藏与停用项） |
| 菜单 | `POST/PUT/DELETE /menus` | 菜单增删改 |
| 部门 | `GET /depts/tree` | 部门树 |
| 部门 | `POST/PUT/DELETE /depts` | 部门增删改 |
| 字典 | `GET/POST/PUT/DELETE /dicts/types` | 字典类型增删改查 |
| 字典 | `GET/POST/PUT/DELETE /dicts/data` | 字典数据增删改查 |
| 字典 | `GET /dicts/data/type/:type` | 按类型取启用字典项（下拉用） |
| 日志 | `GET /oper-logs` | 操作日志列表（模块/操作人/类型/状态/时间筛选） |
| 日志 | `GET /oper-logs/:id` | 操作日志详情（含请求参数与响应体） |
| 日志 | `DELETE /oper-logs` | 批量删除操作日志（单次上限 200 条） |
| 日志 | `DELETE /oper-logs/clean` | 清空操作日志 |
| 日志 | `GET /oper-logs/export` | 导出操作日志 CSV（不含请求参数与响应体） |
| 日志 | `GET /login-logs` | 登录日志列表（账号/IP/状态/时间筛选） |
| 日志 | `DELETE /login-logs` | 批量删除登录日志 |
| 日志 | `DELETE /login-logs/clean` | 清空登录日志 |
| 日志 | `GET /login-logs/export` | 导出登录日志 CSV |

补充约定：

- 字典的「按类型取项」路径特意多一段 `/type`。若写成 `/dicts/data/:type`，
  会与 `/dicts/data/:id` 在 gin 中冲突，启动即 panic。
- 批量删除把 ID 集合放在请求体而非 query，避免数量多时超出 URL 长度限制。
- 日志模块只提供查询与删除：记录由中间件与登录流程写入，
  开放人工新增/修改会让审计失去意义。删除日志本身也会被记一条新日志。
- 操作日志列表不返回 `requestParam` / `jsonResult` 两个 TEXT 字段，
  仅详情接口返回，避免列表响应体膨胀。
- **导出**统一为 CSV（带 UTF-8 BOM，否则 Excel 打开中文乱码）。
  用户导出的手机号/邮箱与列表一致为脱敏值；有行数上限，
  超限报错告知实际条数而非静默截断。导出动作本身记入操作日志。
- **文件上传**（头像）按内容嗅探真实类型，不信扩展名与 Content-Type；
  不接受 SVG（可内嵌脚本）；文件名由服务端随机生成；存本地磁盘并挂数据卷。
  静态访问路径不鉴权（要能放进 `<img src>`），文件名随机不可枚举。
- **用户导入尚未实现**（§10 要求的用户导入），权限点已在 `sys_menu` 中预留。

## 12. 部署与运维方案

### 12.1 部署架构

```
用户 → Nginx → ┬─ 静态资源（前端 dist）
                └─ /api 反向代理 → Gin 服务(:8080)
                                      ├─ MySQL(:3306)
                                      └─ Redis(:6379)
```

### 12.2 部署方式

**统一采用 Docker 部署**，一条命令完成全部编排：

```bash
make deploy        # 等价于 cd deploy && ./deploy.sh up
```

`deploy.sh` 的执行流程：

1. 检查 Docker 环境（自动适配 `docker compose` v2 / `docker-compose` v1）。
2. 首次运行自动生成 `deploy/.env`，内含随机 MySQL/Redis 密码与 JWT/AES/HMAC 密钥（权限 600）。
3. 多阶段构建前后端镜像（后端产出单一静态二进制，运行镜像基于 alpine 且以非 root 用户运行）。
4. 按依赖顺序启动：MySQL / Redis 通过 healthcheck 就绪后才启动 backend。
5. MySQL 首次启动自动导入 `docs/权限系统数据库.sql`（仅数据卷为空时执行，重复部署不会覆盖数据）。
6. 轮询 `/healthz` 确认就绪，打印访问地址与初始账号。

其他命令：

| 命令 | 说明 |
| --- | --- |
| `make deploy` | 构建并启动全部服务 |
| `make deploy-rebuild` | 强制重建镜像（`--no-cache`）后启动 |
| `make deploy-logs` | 跟踪查看日志 |
| `make deploy-ps` | 查看服务状态 |
| `make deploy-down` | 停止并移除容器（**保留**数据卷） |
| `make deploy-destroy` | 停止并删除数据卷（**清空数据库**，需二次确认） |

> **密钥备份**：`deploy/.env` 中的 AES/HMAC 密钥一旦丢失，已加密的邮箱/手机号将无法解密。
> 部署完成后请立即把该文件备份到密码管理器或 KMS。

### 12.3 Nginx 关键配置要点

- 静态资源 `try_files ... /index.html`（支持前端 History 路由）。
- `/api/` 反向代理到后端服务，透传真实 IP。
- 开启 gzip、配置 HTTPS 证书。

### 12.4 环境划分

配置按环境分目录、目录内按关注点分文件，避免所有配置堆在一个大文件里：

```
apps/backend/config/
├── development/    app.yaml  database.yaml  redis.yaml  log.yaml
├── testing/        （同上四个文件）
├── production/     （同上四个文件）
└── rbac_model.conf
```

| 环境 | 用途 | 目录 | 关键差异 |
| --- | --- | --- | --- |
| development | 本地开发 | `config/development/` | Gin debug 模式、SQL 全量日志、text 日志、关闭验证码 |
| testing | 测试联调 | `config/testing/` | release 模式、warn 级 SQL 日志、json 日志、Redis 独立 db |
| production | 生产 | `config/production/` | release 模式、仅 error 级 SQL 日志、更大连接池、强制校验密钥与 CORS |

- 环境由 `APP_ENV` 指定（缺省 `development`），也可用启动参数 `-env`。
- 加载时把目标环境目录下四个文件全部合并；缺任一文件即启动失败。
- 优先级：`config/{env}/*.yaml` < 环境变量 `APP_*`。
- 所有密钥字段在 yaml 中留空，必须由环境变量注入；生产环境还会额外校验
  MySQL 密码非空、`app.mode=release`、CORS 白名单不含通配与 localhost。

## 附：技术难点提示

1. **动态路由刷新丢失**：F5 刷新后 Pinia 清空导致路由丢失，需在路由守卫中判断并重新拉取菜单/重建路由。
2. **数据权限过滤**：建议用 GORM 的 Scopes 封装 `data_scope` 过滤逻辑，避免每个查询手写。
3. **菜单树/部门树递归**：数据库存 `parent_id`，查出扁平列表后在内存递归组装成树，比递归查库高效。
4. **Casbin 与业务权限同步**：角色改权限时需同步刷新 Casbin 策略（`LoadPolicy`）。
5. **前后端 perms 一致性**：按钮 perms 标识需前后端约定统一命名（如 `模块:资源:操作`）。
6. **敏感字段加密查询**：`email`/`phone` 加密后无法直接 WHERE 查询与建唯一索引，需配合 HMAC 盲索引列；模糊搜索能力受限，登录若用手机号/邮箱也要走盲索引匹配（详见 6.4）。
7. **密钥安全**：AES 与 HMAC 密钥必须由环境变量/KMS 注入，严禁入库或提交仓库；预留 `key_version` 以支持密钥轮换。
